# Browser 2D Map Editor: Implementation Plan

## Goal

Add a custom browser-based editing step between acquiring map data and generating a Godot scene:

**Select area → Download or open data → Inspect and edit in 2D → Export to Godot → Generate 3D.**

Build this into the existing `web/` application. Use osm2streets as a reference for street representation and geometry, not as the editor implementation or a required runtime dependency.

All checkboxes below represent proposed work, not completed functionality.

## 1. What “data view” and “realistic view” mean

Yes: a road stored as a centerline plus a width can be displayed either as a line or as its physical footprint. For a straight, symmetric road with a 6 m carriageway, the road edges are 3 m to either side of the centerline. Curves require offset joins; junctions require intersection geometry.

“Realistic” here means a **metric, top-down surface preview**, not photorealism or a guarantee of surveyed accuracy. Missing source attributes require explicit assumptions.

| Feature                   | Data view                                                         | Realistic view                                        |
| ------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------- |
| Road                      | Source/reference line, direction, optional vertices               | Width-aware carriageway polygon                       |
| Building                  | Footprint outline and selected vertices                           | Filled footprint with surface styling                 |
| Attached sidewalk         | Parent road plus side-specific attributes; optional derived guide | Offset sidewalk strip                                 |
| Attached bike lane        | Parent road plus lane attributes; optional derived guide          | Its own strip within the street cross-section         |
| Separate footway/cycleway | Independent source line or polygon                                | Independent width-aware surface                       |
| Junction                  | Connected source endpoints and reference lines                    | Joined road surfaces with explicit junction treatment |

- [x] Keep one editable model behind both views; switching views must not convert or overwrite source geometry.
- [x] Retain a source reference line even if it is not the geometric center of the complete street corridor.
- [x] Define carriageway width separately from total corridor width, which may include sidewalks, buffers, and other strips.
- [x] Compute offsets in meters using an explicit local projection; never buffer longitude/latitude degrees directly.
- [x] Render physical polygons rather than relying on screen-pixel line thickness for realistic widths.
- [x] Mark inferred widths and inferred facilities in the inspector and legend.
- [x] Keep source polygons as polygons; do not unnecessarily derive centerlines from them.

## 2. Existing architecture and integration points

Repository observations informing this plan:

- `web/src/App.vue` already coordinates the selector interface.
- `web/src/components/MapView.vue` is the existing map component; the documented stack is Vue 3, TypeScript, Vite, Bun, and MapLibre GL.
- `web/src/components/ExportControls.vue` currently orchestrates acquisition, downloading, and direct sending to Godot.
- `web/src/composables/useOverture.ts` reads bundled/session caches; its acquisition method returns `null` when no cache matches. It does not currently download arbitrary Overture areas in the browser.
- The Overture fallback in `ExportControls.vue` sends a bounding box to Godot or downloads command metadata, rather than returning feature data to a browser editor.
- `scripts/fetch_overture.py` acquires buildings and transportation segments and combines them into GeoJSON.
- `web/src/composables/useGodotBridge.ts` posts payloads to `/api/import`.
- `godot_project/addons/osm_importer/geojson_parser.gd` already accepts GeoJSON; new surface feature types still need an explicit import contract.
- `godot_project/addons/osm_importer/road_builder.gd` already owns road-width defaults, surface classification, and ribbon geometry. Browser preview and Godot output must not independently infer conflicting widths.

## 4. Canonical editor data model

Use GeoJSON for geographic geometry, with explicit application properties and a small versioned project envelope. Raw input, editable normalized features, and generated display surfaces have different responsibilities.

- [x] Define a project envelope containing schema version, source metadata, selected bounds, projection origin, source features, edit overrides, and editor settings.
  - _Handoff note:_ `ProjectEnvelope` in `types.ts` defines `schemaVersion`, `sourceMetadata`, `selectedBounds`, `projectionOrigin`, `sourceFeatures`, `features`, `editOverrides`, and `editorSettings`. Populated in both `normalizeOverturePayload` and `normalizeOsmPayload`, validated in `validation.ts`, and verified in `useEditorModel.test.ts`.
- [x] Store canonical GeoJSON coordinates in WGS84 longitude/latitude order; use temporary local metric coordinates for geometry calculations.
  - _Handoff note:_ Features and view surfaces store canonical coordinates in WGS84 `[lon, lat]` order (validated in `validation.ts`). All metric offsets, lengths, and areas are calculated via temporary local metric coordinates (`projectToLocalMeters`, `projectCoordinatesToLocalMeters`, `computeLocalMetricLength`, `computeLocalMetricArea` in `projection.ts`) relative to `projectionOrigin` before unprojecting back to WGS84. Verified in `useEditorModel.test.ts`.
- [x] Assign stable, source-qualified feature IDs; preserve parent IDs when splitting multipart features or generating lane surfaces.
  - _Handoff note:_ Feature IDs are stable and source-qualified (`osm_w<id>`, `osm_r<id>`, `ov_<id>`), with `sourceId` and `sourceReference` tracked. Multipart subsegments preserve `parentFeatureId` and `parentSourceId` on `EditorFeature`. Generated lane and carriageway `ViewSurface`s link back to their parent feature via `parentFeatureId` and to their cross-section strip via `stripId`, surfaced in `useEditorModel` and GeoJSON exports. Verified in `normalization.test.ts` and `useEditorModel.test.ts`.
- [x] Define explicit semantic kinds such as building, road, sidewalk, bike facility, and junction. Polygon geometry alone must not imply “building.”
  - _Handoff note:_ `SemanticKind` in `types.ts` defines explicit semantic kinds (`'building'`, `'road'`, `'sidewalk'`, `'bike_facility'`, `'bike_lane'`, `'junction'`, `'unsupported'`), and every `EditorFeature` has an explicit `kind: SemanticKind`. `determineOvertureSemanticKind` and `determineOsmSemanticKind` in `normalization.ts` and `validateImportPayload` in `validation.ts` classify features by explicit domain attributes. Polygon and MultiPolygon geometries without building attributes are never inferred or normalized as buildings. Tested and verified in `normalization.test.ts`.
- [x] Store normalized values with units and per-value provenance: source-provided, inferred, or user-edited.
  - _Handoff note:_ `Provenance` type in `types.ts` defines `'source' | 'source_provided' | 'inferred' | 'user_override' | 'user_edited'`. Normalized profiles (`RoadProfile`, `BuildingProfile`, and `CrossSectionStrip`) store normalized values wrapped in `ProvenanceValue<T>` with explicit units (`'m'`, `'count'`, `'levels'`, `'m²'`, `'km/h'`, `'mph'`) and per-value provenance. `FeatureInspector.vue` surfaces units and provenance badges (`(Source)`, `(Inferred)`, `(User Edited)`), and supports inline interactive editing of carriageway width, building levels, and height. `useEditorModel.ts` tracks user edits (`updateCarriagewayWidth`, `updateBuildingHeight`, `updateBuildingLevels`, `updateRoadLanes`), marks edited properties as `'user_edited'`, updates road strip offsets and corridor widths, stores overrides in `editOverrides`, and supports reverting to source features. Verified in `normalization.test.ts` and `useEditorModel.test.ts`.
- [x] Represent unknown facility presence distinctly from explicit absence and known presence.
  - _Handoff note:_ `FacilityPresence` type in `types.ts` defines `'present' | 'absent' | 'unknown'`. `FacilityPresenceDetails` and `CycleFacilityPresenceDetails` represent overall and per-side (`leftPresence`, `rightPresence`) presence states distinctly. In `normalization.ts`, known presence (e.g. `sidewalk:both=yes`, `cycleway:right=lane`, Overture subclass rules), explicit absence (e.g. `sidewalk=no`, `cycleway=no`, Overture prohibited access restrictions), and unknown presence (untagged facilities) are normalized with correct provenance and presence flags. `FeatureInspector.vue` surfaces distinct states and badges (`Present`, `Explicitly Absent`, `Unknown`). Verified in `normalization.test.ts`.
- [x] Represent a street cross-section as ordered strips with kind, side, width, direction where relevant, and lateral placement relative to the source line.
  - _Handoff note:_ `buildRoadCrossSectionStrips` in `normalization.ts` constructs cross-section strips ordered from left to right across the roadway. Each strip specifies `kind` ('carriageway', 'sidewalk', 'bike_lane', etc.), `side` ('left', 'center', 'right'), `widthMeters` with units and provenance, `direction` where relevant ('forward', 'backward', 'both'), signed `offsetMeters`, and `lateralPlacement` (`offsetMeters`, `innerOffsetMeters`, `outerOffsetMeters`, `orderIndex`). `recalculateRoadStrips` updates lateral placements and maintains left-to-right strip ordering when profiles are edited. `FeatureInspector.vue` displays ordered cross-section strips with badges, widths, directions, and lateral placement offsets. Verified in `normalization.test.ts`.
- [x] Define left/right relative to source coordinate order and preserve that convention through direction changes and exports.
  - _Handoff note:_ In `types.ts`, `LateralPlacement` and `CrossSectionStrip` document and enforce that `side: 'left' | 'right'` and lateral placement offsets (`negative = left`, `positive = right`) are strictly relative to source coordinate sequence (+90° normal for left, -90° normal for right). In `useEditorModel.ts`, `updateRoadDirection` changes travel direction (`forward` | `backward` | `both`) while strictly preserving left/right strip associations with the source coordinates; `reverseRoadGeometry` inverts source coordinates, swaps strip sides, inverts direction, swaps sidewalk/cycle facilities, and recalculates lateral offsets to preserve physical layout relative to the new coordinate sequence. `surfacesGeoJSON`, `exportSurfacesGeoJSON`, and `exportProjectEnvelope` preserve `side`, `direction`, `lateralPlacement`, and `coordinateOrderConvention: 'left_right_relative_to_source_coordinates'`. `FeatureInspector.vue` surfaces direction and buttons to cycle travel direction or invert line geometry. Verified in `useEditorModel.test.ts`.
- [x] Keep derived surface IDs linked to their editable parent feature; selecting a bike-lane polygon must resolve to its own strip within the road profile.
  - _Handoff note:_ Derived surfaces retain `parentFeatureId`, `stripId`, and formatted unique IDs (`${feature.id}_strip_${strip.id}`). In `useEditorModel.ts`, `selectSurface` resolves any surface ID to its editable parent feature and specific strip (`selectedFeatureId`, `selectedFeature`, `selectedStripId`, `selectedStrip`, `selectedSurfaceId`). In `surfacesGeoJSON`, `isStripSelected` and `isSurfaceSelected` distinguish the selected strip from its parent corridor. `MapView.vue` connects polygon/line click events to `selectSurface` and adds an `editor-surfaces-strip-highlight` layer. `FeatureInspector.vue` highlights selected strips with interactive strip-level width editing via `updateStripWidth`. Verified in `useEditorModel.test.ts`.
- [x] Separate display visibility, export inclusion, and physical facility presence. Hiding a sidewalk must not delete it or change the road width.
  - _Handoff note:_ In `types.ts`, `DEFAULT_LAYER_VISIBILITY` and `DEFAULT_EXPORT_INCLUSIONS` define independent visibility and export inclusion states. In `useEditorModel.ts`, `setLayerVisibility`, `toggleLayerVisibility`, `setExportInclusion`, and `toggleExportInclusion` control display and export independently without mutating `project.features` or any `roadProfile`. `surfacesGeoJSON` filters displayed surfaces by `layerVisibility` while strictly preserving physical strips, carriageway width, corridor width, and presence in the canonical model. `exportSurfacesGeoJSON` and `exportProjectEnvelope` respect `exportInclusions` independently of display visibility. `LayerPanel.vue` provides interactive visibility toggles per layer group with notices indicating physical profile preservation, and `ExportControls.vue` provides non-destructive export inclusion toggles. Verified in `useEditorModel.test.ts`.
- [x] Keep original input immutable and edits reversible; recompute derived geometry from the effective edited model.
  - _Handoff note:_ `sourceGeometry` and `sourceFeatures` in `ProjectEnvelope` are kept strictly immutable across edits. Line coordinate reversals and geometry adjustments write to `effectiveGeometry` (`reverseRoadGeometry`, `updateFeatureGeometry`), leaving original source geometry and reference nodes untouched. All user edits are tracked in `editOverrides`. View surfaces and exports (`viewSurfaces`, `surfacesGeoJSON`, `exportSurfacesGeoJSON`) recompute presentation and polygon strips dynamically from the effective edited model. Individual features can be reverted via `revertFeatureOverrides` (surfaced via "Revert to Source" buttons in `FeatureInspector.vue`), and all edits can be reverted via `revertAllOverrides`, restoring original source geometries, profiles, and derived display surfaces. Verified in `useEditorModel.test.ts`.
- [x] Reject unsupported project schema versions with a clear message rather than interpreting them as ordinary source GeoJSON.
  - _Handoff note:_ Payloads containing `schemaVersion` or `schema_version` (or candidate project envelope structures) are recognized as versioned project files rather than raw source data. In `validation.ts`, `validateImportPayload` checks `isSupportedSchemaVersion` against `SUPPORTED_PROJECT_SCHEMA_VERSIONS` (currently `['1.0.0']`); unsupported versions or candidate envelopes with missing schema versions are explicitly rejected with actionable error messages (`Unsupported project schema version...`) and never fall back to `isOvertureGeoJson` or raw GeoJSON feature inspection. `parseOvertureData` in `useOverture.ts` explicitly detects project envelopes and rejects unsupported schema versions rather than parsing them as Overture FeatureCollections. `normalizeOverturePayload` and `normalizeOsmPayload` in `normalization.ts` throw clear errors if passed project envelope payloads. `EditorToolbar.vue` and `ExportControls.vue` validate project payloads before replacement and alert the user without falling through to ordinary GeoJSON normalizers. Verified in `validation.test.ts`, `useOverture.test.ts`, `normalization.test.ts`, and `useEditorModel.test.ts`.

## 12. Delivery order
